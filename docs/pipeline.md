# Pipeline Guide

The runnable operational workflow is the canonical six-stage pipeline:

```text
discover → scope → prepare → evidence → adjudicate → report
```

These six keys are the entire public CLI and UI vocabulary. The pipeline is DOI-first only; manual shortlist/tracked-claim starts are removed. There is no `curate` stage and no sampling.

## Start and resume

```bash
npm run dev -- pipeline --input path/to/dois.json
npm run dev -- pipeline --input path/to/dois.json --seed-pdf path/to/seed.pdf
npm run dev -- pipeline --input path/to/dois.json --stop-after evidence
npm run dev -- pipeline --run-id <uuid>
npm run dev -- pipeline --run-id <uuid> --rerun-from scope
npm run dev -- pipeline --input path/to/dois.json --max-cost 4
npm run dev -- pipeline --input path/to/dois.json --batch
npm run dev -- pipeline --input path/to/dois.json --census --max-cost 40
```

The input is a JSON object with a nonempty DOI array:

```json
{ "dois": ["10.0000/example"] }
```

Estimated spend is in `cost-summary.json` at the run root, rewritten after every model call, and each stage logs its own cost and the run's total when it finishes. `--max-cost <usd>` stops sending model requests once the run's estimated spend, earlier attempts included, reaches the limit: the stage in progress fails and the run can be resumed with a higher limit. Requests already in flight still finish, so a run can pass the limit by up to `modelConcurrency` requests. The limit is not part of the run config, so raising it on resume changes nothing scientific.

### Census (`--census`)

`--census` analyzes every citer instead of a sample. It is shorthand for two run-config settings, not a third: `discover.probeBudget: "all"`, which probes every enumerated citing work (still capped only by `neighborhoodLimit`), and `discover.candidateSelection.mode: "all"`, which makes every candidate a family with no family cap or record budget. `--probe-budget all` sets the first alone; the UI new-run form has a "Probe every citer" box and a candidate-selection menu. `--census` cannot be combined with `--probe-budget` or the portfolio flags (`--min-families`, `--max-families`, `--max-prepared-records`). A census of a seed with a few thousand citers is a large spend; combine it with `--max-cost` and, for half price, `--batch`.

### Batch transport (`--batch`)

`--batch` sends model requests through Anthropic's Message Batches API, which bills input, output, and cache tokens at half the list price. It changes only the transport under the provider (`src/integrations/batch-transport.ts`): each request is built, validated, retried, cached, and classified exactly as a direct call, and prompts, settings, and artifacts are the same. Like `--max-cost` it is not part of the run config, so a resume can turn it on or off.

- **How it works.** Under `--batch` each stage queues all its model requests at once; the stages are given unbounded concurrency for that attempt, and the saved `modelConcurrency` is untouched. The queue is submitted as one batch once no request has joined it for 2 seconds (or at 10,000 requests or 200 MB), then polled every 15 seconds, doubling to once a minute. Each caller gets back its own result. An errored item raises the error a direct call would, so a bad request still fails the stage and an overloaded one is retried; expired and canceled items were never processed and are resent.
- **Small queues go direct.** A queue that goes quiet with fewer than five requests is sent as direct requests at list price, so a lone clustering call, a retry, or a handful of prompt-cache writes does not wait minutes for a batch.
- **Latency.** Each round of requests waits for its batch: usually minutes, at most 24 hours. A stage that sends in rounds waits once per round. Scope grounding and whole-paper adjudication send each seed's first request alone so it writes the prompt cache, then the rest; under `--batch` that costs one extra round per stage, sent direct when the run has fewer than five seeds.
- **Cost.** A call answered through a batch carries `transport: "batch"` on its call record and is priced at half; `cost-summary.json` counts these per stage (`batchCalls`) and the stage cost log says how many there were. `--max-cost` still holds, approximately: because a whole stage is queued before anything is billed, each batched request reserves an expected cost when it is queued and releases it once its real cost is recorded. The reservation prices a cached shared prefix as a cache read (as a cache write for the first request seen with that prefix), the rest of the prompt as uncached input at about four characters per token plus 300 tokens, and output at twice the mean of this attempt's completed calls with the same purpose and model, never under 2,000 tokens nor over the request's cap, all at batch price. A request that would take billed plus reserved spend past the limit is refused with `spend_limit`. Measured outputs average 345–540 tokens, so the 2,000-token floor dominates: a 2,500-record whole-paper adjudication stage that really costs about $14 reserves about $32 at its peak, so it needs a limit of about 2.3 times its real cost. The limit is not a hard cap: if real outputs average well above the reservation, spend can pass it by the difference across everything already queued.
- **Prompt caching.** Batch savings on whole-paper adjudication and seed grounding depend on cache hits inside the batch. Batched shared prefixes are written with the 1-hour cache TTL rather than 5 minutes, because a batch can wait longer than five minutes after the seed's first request wrote the cache. A 1-hour write costs twice the input price instead of 1.25 times; it is paid once per seed. If the cache is missed, each record pays full input for the seed text (about 22k tokens, about $0.022 per record at Sonnet batch price), which makes a batched record cost about 2.4 times a direct one. `cacheReadTokens` in `cost-summary.json` shows whether the hits happened.
- **Resume and crashes.** A submitted batch is billed even if the process dies before reading it. Every submitted request's `custom_id` (a SHA-256 of its exact body, `anthropic-version`, and `anthropic-beta`) is recorded with its batch id in the `llm_batch_requests` table. When a later run or resume sends the identical request, it waits on that batch, or takes a result already stored, instead of paying again. Rows are deleted once their result reaches a caller, and rows older than 29 days (the API's results retention) are resubmitted. A resume whose settings changed sends different requests, which are new. The one gap is a crash between the API accepting a batch and the database recording it.

Unknown flags and stage names are ordinary invalid input (no legacy aliases). A resumed run loads and validates the saved canonical artifact chain before continuing.

## Stages

### Discover

Discover establishes a lossless, declared citing-neighborhood observation boundary. It enumerates the whole citing neighborhood first, metadata only: OpenAlex pages of 200 sorted by publication date (plain `page=` paging, which needs no API key and reaches 10,000 works; the provider's default order is skewed toward older citers and shifts between requests). `neighborhoodLimit` (default 10,000, `--neighborhood-limit`) is only a safety cap; a neighborhood larger than it is recorded as `truncated`, as is one where a reordered page repeated a work. Every enumerated work becomes a citing-paper record, and the probe set (`probeBudget`, default 100) is drawn from all of them. Sampling covers a frame: the works the provider does not mark closed or abstract-only, since the rest are mostly never read and could not be represented by a random draw. Frame works are grouped into year-band × type-group strata (article, which includes preprints; review; other, the long tail of errata, editorials, chapters and the like). The budget goes to strata one probe at a time, each to the stratum where a probed work would otherwise stand for the most frame works, so every stratum gets one probe before any gets a second and the weights end up as even as the budget allows. Within a stratum works are taken in a fixed pseudo-random order (the content-hash record ID), never the provider's. Budget left once the whole frame is probed goes to works outside it, abstract-only first; they add records but no weight. Each neighborhood records its `probeStrata`: per stratum the enumerated, frame, probed and probed-frame counts and the inclusion probability π = probed frame works / frame works (null for a stratum with no frame works), which Report weights by. Probed papers are fetched, parsed, and harvested `discover.fetchConcurrency` at a time (default 6, `--fetch-concurrency`); results are appended in neighborhood order, so the artifact is byte-identical at any value and a resume ignores the setting.

It preserves every returned citing-paper disposition, citation occurrence, extraction outcome, attributed claim, and candidate. Seed occurrences are one per citation group whose exact `targetRefIds` include the seed; sibling refs remain bundle metadata only. Extraction is told the seed's resolved author-year label and any bundle it shares, and is instructed to extract only from the sentence carrying the seed's marker. Extracted claim `supportSpanText` values are exact-verified against the occurrence `rawContext` and persisted as offset-bound `supportSpan` objects when verification succeeds; mismatches leave the claim without a verified span. Extracted claims are then clustered per seed by a model equivalence pass (`canonicalizeClaims`): claims that attribute the same underlying seed finding join one candidate even when they differ in wording, strength, or scope, so a family is one finding rather than one paraphrase and prevalence counts real cross-citer repetition. When a seed's claims fit one block (150 claims, about 20k input tokens) one request clusters them all. Otherwise clustering runs in two levels (`src/pipeline/claim-clustering.ts`): claims with the same normalized text become one unit; units are split into blocks of at most 150 by BM25 similarity, each block seeded by the heaviest unassigned unit and filled with its unassigned neighbours whose score reaches a quarter of the seed's score against itself, with blocks under half full packed together whole; each block is clustered by the same prompt, `modelConcurrency` at a time (so `--batch` batches them), listing one representative claim per unit; and the block clusters are merged by the same prompt over one representative claim per cluster, blocked the same way and repeated in rounds until one request holds every representative or a round joins nothing. Every request's input is fixed by the claims and the previous round's replies, read in block order, so families are identical at any concurrency and in any completion order, and every request goes through the exact-result cache, so a resume pays nothing for finished blocks. The candidate records how its members were judged equivalent: `equivalence.method` is `model` (one request, with a `repairNote` when unknown, duplicate, or omitted claim references were repaired deterministically), `blocked_model` (the seed's `blockCount`, the block requests that clustered its claims and the merge requests that saw them, each with its own `repairNote`, a `fallbackReason` when that request failed and fell back to exact text in the block or to no joins in the merge, or `single_claim` for a one-claim block), or `exact_normalized_text` with a `fallbackReason` when the single request failed. Candidate selection uses an adaptive 15–25 family portfolio with deterministic prevalence/specificity/confidence/novelty annotations; the prepared-record budget and novelty floor only bind once the family minimum is met, and citation groups are keyed by source locator so groups in different paragraphs stay distinct. Lexical redundancy can still defer near-duplicate candidates. Selection mode `all` instead selects every candidate through the same decision ledger, each with its annotation and the reason, ranked by citing papers, citation groups, and claims that restate it. Grounding is intentionally deferred.

### Scope

Scope consumes verified Discover output, explicitly accounts for every candidate, freezes each selected family’s exact source-claim and citation-occurrence membership, and materializes immutable seed text once per seed. Each seed-text block records a coarse `sectionRole` (abstract, introduction, methods, results, discussion, figure, table, other) and the number of in-text citations the seed itself makes in that block, so later stages can tell the seed's own findings from its summary of prior work. Grounding is an annotation: `not_found`, unavailable text, or a provider failure does not silently remove a frozen family.

### Prepare

Prepare consumes Scope and its exact Discover ancestor. It emits exactly one stable record for every family × citation-occurrence pair, preserving both the complete family ledger and the occurrence-local claim set. Family-level data is stored once on the payload — the Scope families, their Discover seeds, candidates, and claims, and the citing papers of the prepared occurrences — and each record refers to it by id: a record holds only its occurrence, the ids of the family candidates and claims that belong to that occurrence, and its classification, so its size does not grow with its family's. `resolvePreparedRecords` joins the references back for consumers; record IDs are still the family × occurrence hash. Role classification is two-pass. The deterministic regex pass runs first: it prefers verified support-span text and takes the weakest per-claim extraction confidence as the occurrence confidence, so low-information citations reach `skip_low_information` rather than the manual-review queue. Occurrence-local claims missing a verified span are queued as `manual_review_extraction_limited` and never reach a model, because there is no verified text to show one. Every other `unclear` verdict — the deterministic classifier's largest single loss — goes to `prepare.roleClassifierModel`, `modelConcurrency` requests at a time with results kept in input order (so `--batch` batches them and the artifact is identical at any concurrency), (Haiku by default) with the verified span, the marked sentences, and the section heading, and comes back as one of the same five roles; the record is then `classified` with a `model` execution. A model that is also unclear, or that fails or replies unusably, leaves the record `manual_review_role_ambiguous` with its call recorded. Classification failures and ambiguous roles remain typed records; they are not sampled away.

### Evidence

Evidence consumes Prepare and Scope. It retrieves only from immutable Scope seed text and emits one outcome per Prepare record. BM25 queries are built from occurrence-local atomic claims, with the Scope family claim as a declared fallback/secondary query. The two rankings are fused by reciprocal rank (raw BM25 scores are not comparable across queries) and capped at `bm25CandidateLimit`; relevance reranking (on by default) is a separate immutable ranking that sees each chunk's block kind, section role, and whether the block cites other work, but not BM25 scores or ranks. Scope grounding pins, when present, lead the selection in both the BM25 and reranked branches (`rankingSource` ends in `_with_scope_pins`), ordered by document position. When verified pins fill `selectionLimit`, Evidence preserves that exact pin-only packet and records `skipped_pins_fill_selection` without calling the reranker; Report counts these skips separately. Otherwise reranking produces a separate immutable ranking, and content-hash reuse may share work across records without collapsing them. The tokenizer is Unicode-aware, keeps decimals and single-character numbers, and folds simple plurals. `bm25CandidateLimit` and `selectionLimit` are exposed in CLI/UI.

### Adjudicate

Every canonical model call uses provider-enforced structured output (`generateObject`) against the adapter's own response schema. The provider only sees the shape (Anthropic rejects bounds, `oneOf`, and defaults), so the reply is validated locally against the full Zod schema; a reply that still fails, or a completion cut off at the token cap, is a non-retried `invalid_output`, as is a candidate number that names no chunk. Each request body stores its prompt text once, so any call can be reproduced from the artifact alone.

Adjudicate consumes Evidence and Prepare. Deterministic gates produce typed `not_adjudicated` outcomes for unavailable evidence, retrieval failure, invalid context, unsuitable roles, broken citation-scope markers, missing verified support spans, and comparable operational conditions. Ambiguous citation roles stay in the manual-review queue (`manual_review_role_ambiguous` / `manual_review_extraction_limited`) and are not auto-routed to the model. By default (`adjudicate.evidence: seed_text`, `--adjudicate-evidence`) the model reads the whole seed text, rebuilt block for block from the Evidence corpus, so Adjudicate takes no input beyond Evidence and Prepare. The seed text is a prompt prefix shared by every record of a seed and cached by the provider; the citing side is the per-record suffix. The model quotes the passages its verdict rests on, and each quote is verified as exact text of the block it names: a quote that is not is dropped and counted, an `F`, `D`, or `U` left with none is `invalid_output`, and an `E` may quote nothing because the paper may say nothing on the point. The outcome records the verified `seedQuotes` and, as `modelCitedChunkIds`, the corpus chunks that hold them, whether or not Evidence selected those chunks. With `selected_chunks`, or for a seed text over 400,000 characters, the model sees only the chunks Evidence selected and cites them by number. Either way each seed block or chunk is shown with its section role and a flag when it cites other work, and the model is told that only results, figure, table, or abstract text can establish the seed's own finding. The gates are the same in both modes, so a record Evidence could not retrieve for is still not adjudicated. Citation-scope markers are anchored to exact verified support spans and the resolved reference identity; an unverified target remains unmarked and is gated to manual review, including in a single-sentence context. The marked text is windowed only after targeting so an unrelated citation with the same year cannot redirect it. A window whose every sentence is attributed to the seed is wrapped whole and stays eligible. Eligible packets receive one categorical model request yielding `F`, `D`, `E`, or `U`; confidence never routes to another model or method. `adjudicate.effort` sets adaptive thinking effort (`high` by default) and is exposed on the CLI as `--adjudicate-effort` and in the UI form, as is the evidence setting. Each adjudicated outcome also records the model's `citingAssertion` and `sourceStatement`, and for `D` verdicts one to three categorical `mutationKinds` (scope, population, certainty, causality, conditions, endpoint, generality, entity, magnitude, temporality) plus a `direction` (`strengthened`, `weakened`, `shifted`; `none` on non-`D` verdicts); these describe the mutation and never route the verdict. The occurrence-local claim set is bound from Prepare, not echoed by the model. Adjudicated outcomes also record deterministic `evidenceSufficiency` / optional `evidenceLimitation` diagnostics (for example figure-only support) without inventing a new verdict mode.

This method is **uncalibrated**. A completed run is not a validated scientific result and must not be used for trust claims before blinded human calibration.

### Report

Report consumes and tamper-verifies the full five-artifact chain. It writes authoritative JSON with the scientific content first: `familyMutations`, one entry per scoped family carrying the seed finding, its verified grounding spans, and every citing restatement in publication order with verdict, mutation kinds, and the adjudicator's citing/source statements. It also writes funnel counts, rates, and per-record traces, then renders Markdown from that validated JSON with the families section leading. Markdown lists every restatement and traces every record only when the run has at most 200 records. A larger run's Markdown summarizes each family instead: its counts, each verdict's share of its adjudicated records, one grounding span, and up to two restatements per verdict (D and E first, with the adjudicator's statements, then U and F, earliest citing papers first), then names where in the JSON the rest are; the per-record trace section points to `recordTraces`. Its size then follows families, not records: about 4,400 lines for a synthetic 3,000-record, 120-family run, against about 16,000 listing every record. The JSON stays complete. Rates are reported both per record and per unique family × citing-paper × claim unit (`verdict_*_unique_rate`), and the Discover funnel records the probe sampling design per seed and year-band × type-group stratum, with each stratum's frame size and inclusion probability; the Markdown states what share of the enumerated works the frame is. `weightedRates` (`verdict_*_weighted_rate`) count each adjudicated record from a frame work 1/π of its stratum and so estimate F/D/E/U rates over the frame, assuming full-text loss within a stratum is unrelated to fidelity and taking the families as selected from the probed sample; records from works outside the frame are left out. Each weighted rate carries its weighted numerator and denominator beside its sample counts (the frame records it rests on), while `rates` keep the honest observed counts over every adjudicated record. Verdict counts are also split by evidence regime (`verdictCountsByRankingSource`) so scope-pinned and unpinned records can be compared before pooling. Funnel accounting includes unique citing-paper/group coverage, verified vs missing claim support spans, unique family × citing-paper × claim units, packet-quality and evidence-sufficiency diagnostics, adaptive portfolio deferral reasons (family cap, record budget, lexical novelty), manual-review queue splits, and gate-code counts. `F`/`D`/`E`/`U` rates use adjudicated records as their denominator; operational non-verdicts are not verdicts.

## Run behavior

Within a stage, model calls run side by side: `modelConcurrency` (default 6, `--model-concurrency <n>`) bounds how many extraction, clustering, role-classification, grounding, rerank, or adjudication requests are in flight. Results are appended in input order, so an artifact is byte-identical at any concurrency and the setting never enters identity. Scope sends the seed text as a cached prompt prefix, so its first grounding call per seed runs alone and the rest fan out once the cache is written; identical rerank requests issued at the same time share one call. Discover's citing-paper fetching and GROBID parsing have their own bound, `discover.fetchConcurrency` (default 6), one global limit across providers: the full-text fetcher has no per-provider spacing, the HTTP client backs off on 429s, and PDFs reach GROBID at most `GROBID_CONCURRENCY` at a time (default 2, an environment setting, not run config), because a local container timed out parsing with six fetched side by side. A PDF waiting for a GROBID slot has not started its 30-second request timeout. A fatal provider error stops new dispatch, so it costs at most `modelConcurrency` calls (or `fetchConcurrency` fetches).

Fresh and resumed runs create or use `data/runs/<runId>/`. Every succeeded stage is reloaded through its current-version schema and checked for content-hash and lineage consistency before a later stage runs. A failed stage blocks downstream stages.

Old SQLite rows and run directories from the former seven-stage executor are unsupported and may need deletion/recreation. Do not attempt to convert old shortlist, screening, extraction, classification, curation, or support-style adjudication artifacts into this pipeline. Legacy orchestration modules have been deleted from the source tree.
